# Qt 组件代码评审

两段式：机械性错误交给脚本，语义问题交给分析。顺序不能反——先让脚本把
「import 带版本号」「颜色字面量」这类噪声清掉，人工分析才有预算看真正的问题。

## 范围判定

| 说法 | 范围 |
|---|---|
| "这次改动" / "提交前" / "staged" | diff 范围：只查变更文件与变更行 |
| "看下这个文件" | 该文件全量 |
| "审查 src/components" | 该目录下全部 `*.qml` |

diff 范围先取变更文件清单（`git diff --name-only` / `--cached`），只对 `.qml` 文件执行。

## Phase 1：确定性检查

```bash
python3 <本 skill 目录>/scripts/qt_component_lint.py --summary <路径或目录>
```

- 默认按 Qt 6 判定；确认是 Qt 5 项目时加 `--qt=5`（版本号规则会失效）。
- 输出是**候选**，不是判决。逐条确认，确认不了的标为「待验证」而不是直接报缺陷。
- 报告里只写确认过的；不逐条复述规则表。
- 想看规则全集：`--rules`。

## Phase 2：语义深挖

规则表在 [deep-rules.md](references/deep-rules.md)，按域分组（A1–A6、W1）。

- 范围 ≤ 800 行 QML / 500 行 C++：**在主上下文内联做完**，只读命中的文件。
- 超过时：按文件切成等量分片，用 Agent 工具并行处理，每个子任务只传
  「deep-rules.md 绝对路径 + 要用的章节号 + 文件路径」，**不要把代码粘进 prompt**。
- 不要重复报告 Phase 1 已列出的同一行问题。

### Token 纪律

1. 指向路径与行号，不粘贴大段源码。
2. 先读 import 与组件骨架，确认技术栈与版本，再读细节。
3. 只为追踪具体符号（某个 id、role、C++ 类型）才打开其他文件。
4. 报告写结论与依据，不写思考过程。

## 置信度

| 区间 | 含义 | 处理 |
|---|---|---|
| 80–100 | 缺陷代码路径在已读源码中可见，或由 Qt 文档化行为确认 | 作为「缺陷」报告 |
| 60–79 | 是否成缺陷取决于看不到的信息（C++ 类型、上下文属性、运行时数据、使用方意图） | 作为「待验证」报告，总数不超过 5 条 |
| < 60 | 只是怀疑，没有代码路径支撑 | 丢弃，不写 |

宁少勿滥。三条确认的缺陷比十二条猜测有用。

## 输出格式

```markdown
## 评审结论
<一句话：整体可用 / 有阻塞问题 / 需要重构>

## 缺陷（按影响排序）

### [D-001] <一句话标题>
- 文件：`path/to/File.qml:42`
- 分类：绑定 / 布局 / 委托 / 生命周期 / 令牌 / C++ 边界 / Widgets
- 置信度：92/100
- 问题：<具体错在哪，引用关键行>
- 依据：<为什么这是缺陷：Qt 行为 / 代码路径>
- 修复方向：<怎么做，说明取舍；除非用户要求，不给完整补丁>

## 待验证

### [I-001] <标题>
- 文件：`path:line`
- 置信度：68/100
- 疑点：<怀疑什么>
- 无法确认的原因：<缺什么信息>
- 怎么验：<具体动作>

## 已确认无问题
<一句话带过检查过的域；没有就省略>

## 建议优先处理
1. ...
2. ...
```

## 边界

- **只读**：不修改代码。用户说「顺手修掉」时才进入修复模式，且修复前先确认范围。
- **不臆造**：拿不准的 Qt 行为标「待验证」，不要用「通常」「一般」包装猜测。
- **项目约定优先**：周边代码有稳定且不同的写法时，报「与项目约定不一致」而不是「错误」。
- **不给全量重写**：除非用户明确要求，评审产出是问题清单 + 修复方向，不是新版本代码。
